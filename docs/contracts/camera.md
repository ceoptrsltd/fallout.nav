# Контракт: fnav-camera (агент E) ↔ fnav-core (A) ↔ система (G)

## Конвейер

```
OV5647 2592×1944 (полный кадр) ─ISP→ main 1440×1080 YUV420 ─► H264Encoder (аппаратный, 15 fps, GOP 15, bitrate из настроек)
                                                                 ├─► регистратор MPEG-TS (10 мин, fsync 1 с)
                                                                 └─► RTSP-публикация в MediaMTX rtsp://127.0.0.1:8554/cam
                                 └► lores 768×576 ──┬────────────► JPEG (simplejpeg) ► MJPEG http://127.0.0.1:8081/mjpeg
                                                    └─(по требованию)► H264Encoder №2 (аппаратный, live_bitrate_kbps, GOP 1 с)
                                                                       ► MPEG-TS ► http://127.0.0.1:8081/live.ts
```

- Picamera2, `create_video_configuration(main={"size":(out_w,out_h)}, lores={"size":(768,576)}, sensor={"output_size":(2592,1944)}, controls={"FrameRate": fps})`.
  Если на устройстве режим сенсора называется иначе — выбрать режим с полным полем зрения (crop = вся матрица) и максимальным размером. Не допускать обрезанного режима 1920×1080.
- Один процесс владеет камерой. Если камера недоступна — `state="error"`, повтор каждые 5 с.

## Регистратор (главное требование: при обрыве питания теряется ≤ 2 с)

- Формат **MPEG-TS** (`.ts`), H.264 Annex-B, метки времени корректные (PTS/DTS), без звука.
- Сегменты по `camera.segment_minutes` (10 мин). Новый сегмент начинается **с ключевого кадра**.
- **`fsync()` каждые `camera.fsync_interval_s` (1 с)** — по fd файла, вне event loop (поток).
- При старте: последний файл обрезать до кратного 188 байт (и до последнего целого пакета с синхробайтом `0x47`).
- Имена: `{recordings_dir}/YYYY-MM-DD/YYYY-MM-DD_HH-MM-SS.ts` по **локальному** времени системы.
  Если время не синхронизировано (`timedatectl show -p NTPSynchronized` = no, либо год < 2025): `{recordings_dir}/nosync/boot-<boot_id[:8]>_<seq:04d>.ts`.
  После синхронизации времени текущий сегмент не переименовывать; следующий — уже с датой.
- Защита: файл `<name>.ts.lock` рядом (пустой). Защищённые не удаляются автоматически.
- **Очистка (делает E):** пока свободно < `storage.min_free_gb` + запас на 1 сегмент (по битрейту) — удалять самые старые незащищённые `.ts` (кроме текущего), пустые каталоги — тоже. Проверка раз в 30 с и при начале сегмента.
  Кэш тайлов (1 ГБ, A) считается частью занятого места — E его не трогает.
- Нехватка места даже после очистки (всё защищено) → `state="error"`, `error="No space left: all recordings are protected"`, запись останавливается до освобождения.

## Индекс ключевых кадров (`.ts.idx`) и HLS по записи

Нужен, чтобы плеер админки перематывал в любое место записи сразу (`GET /api/recordings/hls/…`, api.md),
без чтения файла от начала. Код — `fnav/camera/tsindex.py` (общий для E и A).

- Рядом с сегментом регистратор пишет `<имя>.ts.idx`: первая строка `fnav-tsindex 1`, затем на каждый ключевой
  кадр строка `<смещение> <pts>\n` — смещение (кратно 188) первого байта записи этого кадра (PAT/PMT, затем IDR),
  PTS 90 кГц. Строка дописывается сразу после записи кадра в `.ts`, без буфера и без `fsync`.
- После обрыва питания индекс может быть короче файла или указывать за конец (файл обрезан при восстановлении):
  fnav-core берёт строки только внутри файла, последнюю перепроверяет, остальное находит поиском по файлу.
- Записи без индекса (сделанные раньше): fnav-core ищет ключевые кадры в самом файле — хвост (4 МБ) подряд,
  остальное выборочно (окно перед местом, где по битрейту и GOP ожидается ключевой кадр через ~3 с; читается
  ~1/10 файла). Результат кэшируется в памяти по (путь, размер, mtime); растущий файл дочитывается.
- `.ts.idx` удаляется вместе с `.ts` (очистка E, восстановление E, `DELETE` A). Список записей его не показывает.

## HTTP 127.0.0.1:8081 (только localhost, без авторизации)

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/status` | `CameraStatus` (fnav/models.py) |
| GET | `/mjpeg` | `multipart/x-mixed-replace; boundary=frame`, кадры lores JPEG, ~15 fps; `?fps=N` (1…30) — прореживание для одного клиента |
| GET | `/live.ts` | `video/mp2t`, живое видео по требованию (см. ниже); 503 `{"ok":false,"error":"…"}`, если камера не работает или второй энкодер не стартовал |
| GET | `/snapshot.jpg` | последний lores-кадр |
| POST | `/protect-current` | `{"ok":true,"segment":"2026-10-20/…ts"}` — создаёт `.lock` для текущего сегмента |
| POST | `/reload` | перечитать `settings.json`; если изменились параметры камеры — перезапустить конвейер (текущий сегмент закрыть корректно) |
| POST | `/restart` | перезапустить конвейер |
| POST | `/motion` | `{"moving": true\|false\|null}` от fnav-core → `{"ok":true,"max_exposure_ms":…}`; предел выдержки ночью (ниже) |

- Настройки E читает из `fnav.paths.settings_file()` (если файла нет — `Settings()` по умолчанию). E файл **не пишет**.
- Встроенный HTTP-сервер — лёгкий (aiohttp не тянуть; достаточно `http.server` в потоке или uvicorn+starlette — на выбор E, но без новых тяжёлых зависимостей).

## Ночная экспозиция

- Тюнинг `<сенсор>.json` (модель — из `/sys/class/video4linux/v4l-subdev*/name`, до открытия камеры) дополняется во
  всех режимах экспозиции ступенью «выдержка до 1 с, затем усиление до 16×» (`picam.night_tuning`). AE доходит до неё,
  только упёршись в штатный максимум (1/fps × 8), — днём картинка прежняя. libcamera читает тюнинг один раз на процесс,
  поэтому таблица неизменна, а реальный предел задаёт `FrameDurationLimits = (1/fps, max(1/fps, предел))` — его можно
  менять на ходу. Выдержка длиннее кадра снижает частоту кадров (PTS — по меткам времени кадров, запись не «ускоряется»).
- Предел: `camera.max_exposure_ms_driving` (66: едем или неизвестно) / `camera.max_exposure_ms_parked` (125: стоим).
  Смена этих полей (`/reload`) применяется без перезапуска записи; счётчик потерянных кадров учитывает длинные кадры.
- «Едем/стоим» решает fnav-core по скорости GPS: ≥ 1,5 м/с — сразу «едем»; < 0,5 м/с дольше 10 с — «стоим»; нет
  скорости — прежнее решение. Ядро сравнивает своё решение с `moving` из `/status` при каждом опросе и шлёт `/motion`,
  если камера не знает (например, после перезапуска).
- `CameraStatus`: `moving`, `max_exposure_ms`, `exposure_ms`, `gain` (аналоговое × цифровое), `lux` — метаданные кадра.
- Замер в фургоне ночью (≈ 4 lux): 66 мс × 8 (было) → 66 мс × 16 вдвое светлее при тех же 15 к/с → 125 мс × 16 ещё вдвое
  (8 к/с); 32× заметно шумнее, сильное шумоподавление почти ничего не даёт.

## Живое видео по требованию (`/live.ts`)

- Отдельный аппаратный H.264 с **lores** (768×576, `camera.fps`, `camera.live_bitrate_kbps` — по умолчанию 800,
  ключевой кадр раз в секунду, SPS/PPS перед каждым). Запускается при первом клиенте, выключается через 5 с после
  ухода последнего: нет зрителей — нет второго кодирования. Все клиенты делят один энкодер.
- Поток начинается с PAT/PMT + IDR; PTS непрерывны и при перезапуске конвейера/энкодера.
  Медленный клиент (очередь > ~6 с) теряет хвост и продолжает со следующего ключевого кадра. Нет данных 15 с — поток
  закрывается (клиент переподключается).
- Запись (main) не зависит от зрителей: второй энкодер добавляется в Picamera2 через `start_encoder(..., name="lores")`
  и снимается из рассылки кадров **до** остановки (иначе поток камеры ждал бы его остановки). Ошибка запуска → 503, в лог.
- Изменение только `live_bitrate_kbps` (`/reload`) перезапускает лишь второй энкодер, запись — нет.
- fnav-core: `GET /api/camera/live.ts` (только с сессией) и `GET /api/camera/mjpeg?fps=N` — потоковый прокси.
  Mock-режим ядра отдаёт синтетический live.ts (PyAV на ПК).

## MediaMTX (конфиг пишет G: `pi/mediamtx.yml`)

- Путь `cam`, источник `publisher` (RTSP push от fnav-camera), RTSP только `127.0.0.1:8554`.
- WebRTC: HTTP (WHEP) `127.0.0.1:8889` (наружу — только через прокси fnav-core), ICE UDP `:8189` на всех интерфейсах.
- **Запись в MediaMTX выключена** (`record: no`) — записью занимается только регистратор E.
- HLS, RTMP, SRT — выключены.

## Режим разработки (на ПК, без камеры)

- `python -m fnav.camera --fake` — вместо Picamera2 источник тестового H.264 (например, ffmpeg `testsrc` → H.264 Annex-B, если ffmpeg есть) или синтетические кадры; MJPEG — тестовая картинка.
- Тест «обрыв питания»: писать сегмент, в случайный момент убить процесс (`SIGKILL`) / обрезать файл на случайном байте → после «перезагрузки» файл обрезается до целых пакетов и полностью декодируется (ffprobe/PyAV), потеря ≤ `fsync_interval_s` + 1 с.
