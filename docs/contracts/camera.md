# Контракт: fnav-camera (агент E) ↔ fnav-core (A) ↔ система (G)

## Конвейер

```
OV5647 2592×1944 (полный кадр) ─ISP→ main 1440×1080 YUV420 ─► H264Encoder (аппаратный, 15 fps, GOP 15, bitrate из настроек)
                                                                 ├─► регистратор MPEG-TS (10 мин, fsync 1 с)
                                                                 └─► RTSP-публикация в MediaMTX rtsp://127.0.0.1:8554/cam
                                 └► lores 768×576 ──┬────────────► JPEG (simplejpeg) ► MJPEG http://127.0.0.1:8081/mjpeg
                                                    ├─(по требованию)► H264Encoder №2 (аппаратный, live_bitrate_kbps, GOP 1 с)
                                                    │                  ► MPEG-TS ► http://127.0.0.1:8081/live.ts
                                                    └─(пока просит fnav-watch, ≤ 4 к/с)► кольцо в общей памяти /dev/shm/fnav-lores ► fnav-watch
```

- Picamera2, `create_video_configuration(main={"size":(out_w,out_h)}, lores={"size":(768,576)}, sensor={"output_size":(2592,1944)}, controls={"FrameRate": fps})`.
  Если на устройстве режим сенсора называется иначе — выбрать режим с полным полем зрения (crop = вся матрица) и максимальным размером. Не допускать обрезанного режима 1920×1080.
- Один процесс владеет камерой. Если камера недоступна — `state="error"`, повтор каждые 5 с.

## Регистратор (главное требование: при обрыве питания теряется ≤ 2 с)

- Формат **MPEG-TS** (`.ts`), H.264 Annex-B, метки времени корректные (PTS/DTS), без звука.
- Сегменты по `camera.segment_minutes` (10 мин). Новый сегмент начинается **с ключевого кадра**.
- **`fsync()` каждые `camera.fsync_interval_s` (1 с)** — по fd файла, вне event loop (поток).
- При старте: последний файл обрезать до кратного 188 байт (и до последнего целого пакета с синхробайтом `0x47`).
- Имена: `{recordings_dir}/YYYY-MM-DD/YYYY-MM-DD_HH-MM-SS.ts` по **локальному** времени системы.
  Если время не синхронизировано (`timedatectl show -p NTPSynchronized` = no, либо год < 2025): `{recordings_dir}/nosync/boot-<boot_id[:8]>_<seq:04d>.ts`.
  После синхронизации времени текущий сегмент не переименовывать; следующий — уже с датой.
  Часовой пояс системы следует за машиной (api.md «Часовой пояс»): обслуживание камеры (`TimeSync.refresh`, ≤ 10 с)
  замечает смену `/etc/localtime` и вызывает `time.tzset()` (`fnav/tz.py` `ZoneWatch`); текущий сегмент сохраняет
  имя, следующий назван по новому местному времени (может оказаться «раньше» предыдущего). Поэтому истинное начало
  каждого сегмента (unix, UTC) — в заголовке его `.ts.idx` (ниже): по имени после смены пояса его не понять.
- Защита: файл `<name>.ts.lock` рядом (пустой). Защищённые не удаляются автоматически (снимает защиту только пользователь).
- **Защита у границы сегмента** (`/protect-current`: охрана, «Protect current» в админке, долгое нажатие кнопки
  GPS-модуля): окно `PROTECT_EDGE_S` = 60 с по меткам кадров камеры. В прошлом сегменте есть кадры моложе 60 с
  (текущий начался меньше минуты назад — подход и кадр «за 5 с» там) — защищается и он; до плановой смены меньше
  60 с — и следующий, как только откроется (если начнётся не позже плановой смены + 60 с: после пропажи видео это уже
  не продолжение).
  Сегмент, закрытый при остановке конвейера меньше 60 с назад, — тоже (новый регистратор о нём не знает). Ответ —
  по-прежнему текущий сегмент; соседи — в лог. `recent=1` — как раньше (ниже, HTTP).
- **Очистка (делает E):** удалять самые старые незащищённые `.ts` (кроме текущего), пустые каталоги — тоже, пока
  свободно < `storage.min_free_gb` + запас на 1 сегмент (по битрейту) **или** все записи вместе (с защищёнными) больше
  `storage.max_recordings_gb` − запас на 1 сегмент. Проверка раз в 30 с и при начале сегмента.
  Кэш тайлов (1 ГБ, A) считается частью занятого места — E его не трогает.
- **Минимум петли.** Петля — незащищённые записи (с текущей). Ради лимита объёма она не сокращается меньше **часа
  записи** по битрейтам из настроек (у передней — с задней, если та пишет: передняя чистит и её записи; 6000 + 4000
  кбит/с ≈ 4,5 ГБ), но и не больше **половины лимита** (иначе лимит не работал бы и без защищённых). Удаляются только
  самые старые: дыр в петле нет, перебор — меньше одного сегмента. Глубже — только ради свободного места (диск правда
  кончается). Без минимума защищённые сверх лимита (каждая тревога защищает текущие сегменты обеих камер, ~450 + 200
  МБ, у границы — и соседние) оставляли бы от петли последние минуты.
- Защищённые + минимум петли > лимита — записи занимают больше лимита, петля держит только минимум:
  `CameraStatus.over_limit = true` (и предупреждение в лог), `protected_gb` — защищённые (у передней — обеих камер),
  `loop_minutes` — сколько минут записи держит петля сейчас (её байты / битрейт из настроек — оценка). Админка
  («Camera», «Recordings») предупреждает: защищённые занимают X ГБ из Y ГБ лимита, без защиты хранятся только
  последние ~N мин — снимите защиту с ненужных. У передней это касается записей обеих камер, у задней — её своих.
- Нехватка места даже после очистки (всё защищено) → `state="error"`, `error="No space left: all recordings are protected"`, запись останавливается до освобождения.

## Индекс ключевых кадров (`.ts.idx`) и HLS по записи

Нужен, чтобы плеер админки перематывал в любое место записи сразу (`GET /api/recordings/hls/…`, api.md),
без чтения файла от начала. Код — `fnav/camera/tsindex.py` (общий для E и A).

- Рядом с сегментом регистратор пишет `<имя>.ts.idx`: первая строка `fnav-tsindex 2`, вторая — `start <unix>`
  (истинное начало сегмента, UTC, с мс — тот же момент, по которому назван файл; при несинхронизированном времени,
  `nosync/`, строки нет), затем на каждый ключевой кадр строка `<смещение> <pts>\n` — смещение (кратно 188) первого
  байта записи этого кадра (PAT/PMT, затем IDR), PTS 90 кГц. Строка дописывается сразу после записи кадра в `.ts`,
  без буфера и без `fsync`. Индексы версии 1 (`fnav-tsindex 1`, без `start`; записи до этой версии) читаются как
  раньше. fnav-core отдаёт `start` как `start_ts` записи (api.md «Записи»).
- После обрыва питания индекс может быть короче файла или указывать за конец (файл обрезан при восстановлении):
  fnav-core берёт строки только внутри файла, последнюю перепроверяет, остальное находит поиском по файлу.
- Записи без индекса (сделанные раньше): fnav-core ищет ключевые кадры в самом файле — хвост (4 МБ) подряд,
  остальное выборочно (окно перед местом, где по битрейту и GOP ожидается ключевой кадр через ~3 с; читается
  ~1/10 файла). Результат кэшируется в памяти по (путь, размер, mtime); растущий файл дочитывается.
- `.ts.idx` удаляется вместе с `.ts` (очистка E, восстановление E, `DELETE` A). Список записей его не показывает.

## HTTP 127.0.0.1:8081 (только localhost, без авторизации)

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/status` | `CameraStatus` (fnav/models.py); `video_age_s` — сколько секунд нет кадров с камеры, с любого потока (`null` — после запуска конвейера ещё не было): охрана по нему видит пропавшую камеру ([alarm.md](alarm.md) «Камера пропала»), экран — есть ли картинка. У задней без основного потока — `state: "error"`, `error` «no main stream (…)», `recording: false`, а `video_age_s` свежий (картинка со второго) |
| GET | `/mjpeg` | `multipart/x-mixed-replace; boundary=frame`, кадры lores JPEG, ~15 fps; `?fps=N` (1…30) — прореживание для одного клиента. Заголовки следующей части уходят сразу за кадром (без `Content-Length`): Chromium показывает часть, только когда пришли заголовки следующей, — иначе экран всегда отставал на кадр (проверено на Chromium 152). Новому зрителю — последний кадр, только если он не старше 0,3 с, иначе следующий |
| GET | `/live.ts` | `video/mp2t`, живое видео по требованию (см. ниже); 503 `{"ok":false,"error":"…"}`, если камера не работает или второй энкодер не стартовал |
| GET | `/snapshot.jpg` | текущий lores-кадр — **только свежий** (≤ 3 с; кодер JPEG пишет ≥ 1 кадра/с и без зрителей): старше — ждём новый ≤ 3 с, нет — 503 `{"error": "No video from the camera"}`, а не стоп-кадр из памяти (камера пропала, задняя выключена). `?before=N` (≤ 3600) — кадр не дальше 2 с от «N секунд назад» из истории хаба (кадры за 12 с до последнего, не чаще раза в 0,5 с, ~1 МБ; хранятся, сколько бы им ни было — последние кадры пропавшей камеры); кадров тогда не было: N ≤ 12 — текущий свежий (камера только что запустилась), иначе 404. Заголовок `X-Frame-Age` — настоящий возраст кадра, с. Охрана берёт кадр за 5 с до события |
| POST | `/protect-current` | `{"ok":true,"segment":"2026-10-20/…ts"}` — создаёт `.lock` для текущего сегмента (у границы — и для соседних, «Защита у границы сегмента»); нет — 409. `?recent=1` (охрана, камера пропала): текущего нет, потому что конвейер перезапущен без кадров, — последний закрытый при остановке конвейера, если он моложе 10 мин (в нём то, что было перед пропажей) |
| POST | `/reload` | перечитать `settings.json`; если изменились параметры камеры — перезапустить конвейер (текущий сегмент закрыть корректно) |
| POST | `/restart` | перезапустить конвейер |
| POST | `/motion` | `{"moving": true\|false\|null}` от fnav-core → `{"ok":true,"max_exposure_ms":…}`; предел выдержки ночью (ниже) |
| POST | `/sound` | задняя с микрофоном: `{"armed": bool}` от fnav-core — стоит ли охрана (громкие звуки пишутся клипами только на ней); у передней — 409 |
| GET | `/sound/events?after=N` | громкие звуки новее `seq` N, старые первыми: `{"events": [{seq, start, dur_s, peak_db, floor_db, clip, clip_start, clip_dur_s}], "seq": n}` |

- Настройки E читает из `fnav.paths.settings_file()` (если файла нет — `Settings()` по умолчанию). E файл **не пишет**.
- Встроенный HTTP-сервер — лёгкий (aiohttp не тянуть; достаточно `http.server` в потоке или uvicorn+starlette — на выбор E, но без новых тяжёлых зависимостей).

## Ночная экспозиция

- Тюнинг `<сенсор>.json` (модель — из `/sys/class/video4linux/v4l-subdev*/name`, до открытия камеры) дополняется во
  всех режимах экспозиции ступенью «выдержка до 1 с, затем усиление до 16×» (`picam.night_tuning`). AE доходит до неё,
  только упёршись в штатный максимум (1/fps × 8), — днём картинка прежняя. libcamera читает тюнинг один раз на процесс,
  поэтому таблица неизменна, а реальный предел задаёт `FrameDurationLimits = (1/fps, max(1/fps, предел))` — его можно
  менять на ходу. Выдержка длиннее кадра снижает частоту кадров (PTS — по меткам времени кадров, запись не «ускоряется»).
- Предел: `camera.max_exposure_ms_driving` (66: едем или неизвестно) / `camera.max_exposure_ms_parked` (125: стоим).
  Смена этих полей (`/reload`) применяется без перезапуска записи; счётчик потерянных кадров учитывает длинные кадры.
- «Едем/стоим» решает fnav-core по скорости GPS: ≥ 1,5 м/с — сразу «едем»; < 0,5 м/с дольше 10 с — «стоим»; нет
  скорости — прежнее решение. Ядро сравнивает своё решение с `moving` из `/status` при каждом опросе и шлёт `/motion`,
  если камера не знает (например, после перезапуска).
- `CameraStatus`: `moving`, `max_exposure_ms`, `exposure_ms`, `gain` (аналоговое × цифровое), `lux` — метаданные кадра.
- Замер в фургоне ночью (≈ 4 lux): 66 мс × 8 (было) → 66 мс × 16 вдвое светлее при тех же 15 к/с → 125 мс × 16 ещё вдвое
  (8 к/с); 32× заметно шумнее, сильное шумоподавление почти ничего не даёт.

## Живое видео по требованию (`/live.ts`)

- Отдельный аппаратный H.264 с **lores** (768×576, `camera.fps`, `camera.live_bitrate_kbps` — по умолчанию 800,
  ключевой кадр раз в секунду, SPS/PPS перед каждым). Запускается при первом клиенте, выключается через 5 с после
  ухода последнего: нет зрителей — нет второго кодирования. Все клиенты делят один энкодер.
- Поток начинается с PAT/PMT + IDR; PTS непрерывны и при перезапуске конвейера/энкодера.
  Медленный клиент (очередь > ~6 с) теряет хвост и продолжает со следующего ключевого кадра. Нет данных 15 с — поток
  закрывается (клиент переподключается).
- Запись (main) не зависит от зрителей: второй энкодер добавляется в Picamera2 через `start_encoder(..., name="lores")`
  и снимается из рассылки кадров **до** остановки (иначе поток камеры ждал бы его остановки). Ошибка запуска → 503, в лог.
- Изменение только `live_bitrate_kbps` (`/reload`) перезапускает лишь второй энкодер, запись — нет.
- fnav-core: `GET /api/camera/live.ts` (только с сессией) и `GET /api/camera/mjpeg?fps=N` — потоковый прокси.
  Mock-режим ядра отдаёт синтетический live.ts (PyAV на ПК).

## Кольцо lores в общей памяти (для fnav-watch)

Камера на охране (docs/contracts/vision.md) берёт lores-кадры без JPEG: `fnav/camera/shmring.py`, файл
`/dev/shm/fnav-lores` (на ПК — во временном каталоге; `FNAV_LORES_RING` — свой путь), mmap с обеих сторон.

- Файл создаёт **читатель** (fnav-watch). Камера раз в секунду проверяет, есть ли он (`stat`), и копирует кадр, только
  пока читатель продлевает в заголовке «хочу до» (монотонные часы, ~3 с вперёд) и не чаще его частоты (4 к/с). Нет
  читателя — ~2 мкс на кадр; копия кадра 768×576 — ~0,5 мс на CM4. Перестал смотреть — сразу «не хочу».
- Заголовок 64 байта (`FNAVRNG1`, версия, 3 слота, ёмкость слота, номер последнего кадра, «хочу до», частота, pid
  камеры); слот — 64 байта (номер begin, время записи по `time.monotonic()`, формат `yuv420`/`rgb`, ширина, высота,
  шаг строки, длина, ExposureTime/AnalogueGain/DigitalGain/Lux из `PicameraSource.exposure` (раз в 8 кадров) или NaN, номер end) и
  данные как у Picamera2 (`yuv420`: (h·3/2, stride)). Без блокировок: писатель пишет begin, данные, метаданные, end,
  потом номер кадра; читатель берёт слот, только если end и begin равны номеру (иначе читает заново).
- Путь внутри камеры — тот же, что для MJPEG: `wants_lores()` / `on_lores()` (`CameraService` раздаёт кадр JPEG-кодеру
  и/или кольцу), поэтому `--fake` (FakeSource) тоже кормит кольцо (`rgb`). Ошибки кольца в потоке камеры не
  выходят наружу (в лог один раз); пересоздание файла (сменился размер) — атомарно, через rename.

## MediaMTX (конфиг пишет G: `pi/mediamtx.yml`)

- Путь `cam`, источник `publisher` (RTSP push от fnav-camera), RTSP только `127.0.0.1:8554`.
- WebRTC: HTTP (WHEP) `127.0.0.1:8889` (наружу — только через прокси fnav-core), ICE UDP `:8189` на всех интерфейсах.
- **Запись в MediaMTX выключена** (`record: no`) — записью занимается только регистратор E.
- HLS, RTMP, SRT — выключены.

## Задняя камера (IP-камера по RTSP)

Тот же сервис вторым экземпляром: `python -m fnav.camera --camera rear` (unit `fnav-camera-rear`, HTTP
`127.0.0.1:8083`, те же маршруты). Настройки — `settings.rear_camera` (`enabled`, `url` rtsp://… без логина, `username`,
`lores_url` — второй поток камеры, `transport`, `record`, `fps`/`bitrate_kbps` — оценки, `mirror`, `lores`: по
умолчанию 25 к/с — задний вид на экране, кадры PAL-кинескопа); пароль — `FNAV_REAR_CAMERA_PASSWORD` в `secrets.env`
(`/etc/fnav/secrets.env`, unit задаёт `FNAV_SECRETS`).

Камера в фургоне — Kruger&Matz Connect C150 (Tuya, плата FH8852V201, RTSP `:8554/profile0` и `/profile1`, ONVIF
`:6688`, логин `admin`). Настроена по ONVIF Media2 (через Media1 она пишет «H264», а шлёт H.265): основной поток
H.264 2560×1440, 25 к/с, ключевой кадр раз в секунду, до 2,5 Мбит/с; второй — H.264 640×360, 25 к/с, до 512 кбит/с;
экспозиция — приоритет частоты, выдержка ≤ 1/25 с. При слабом свете камера всё равно отдаёт ~16,7 к/с (выдержка
1/60 с): её параметры экспозиции в ONVIF, похоже, только для вида. Сброс камеры вернёт H.265 — сервис скажет
`video codec is hevc`.

```
IP-камера ─RTSP/TCP→ процесс fnav.camera.rtsp_pull (PyAV) ─ H.264 как есть ─┬─► регистратор rear/YYYY-MM-DD/…ts (+ .idx)
                       (адрес с паролем — в env FNAV_RTSP_URL, не в ps)     ├─► RTSP-публикация в MediaMTX rtsp://127.0.0.1:8554/rear
                                                                            └─► /live.ts — тот же поток
          ─ декодирование по требованию (программное) ───────────────────► lores yuv420p ─┬─► JPEG ► MJPEG /mjpeg, /snapshot.jpg
                                                                                          └─► кольцо /dev/shm/fnav-lores-rear ► fnav-watch
```

- **Без перекодирования**: запись, MediaMTX и `/live.ts` — исходный H.264 камеры (у ключевого кадра без SPS/PPS —
  SPS/PPS из SDP). Камеру нельзя попросить о ключевом кадре: новый сегмент — с очередного (GOP ожидается ≤ 4×fps).
- **Один клиент у камеры**: подключается только сервис; админка смотрит через MediaMTX (путь `rear`). Второй поток
  камеры (`lores_url`) открывается отдельным процессом, только пока нужны малые кадры, закрывается через 10 с.
- **Потоки независимы** (с `lores_url`): экран, снимки и fnav-watch — на втором, запись, MediaMTX и `/live.ts` — на
  основном. Основной отвалился (камера его не отдаёт — бывает после её перезапуска; обрыв), а второй работает —
  конвейер не перезапускается: текущий сегмент закрывается, источник сам переподключает основной (пауза 5 → 30 с),
  запись продолжится новым сегментом с ключевого кадра. В статусе — ошибка «no main stream (…)», `video_age_s` свежий
  (картинка есть). Второй отвалился — переподключение с паузой 1 → 30 с. Нет картинки ни с одного потока
  `frame_timeout` (15 с) — перезапуск всего, как раньше. Без `lores_url` картинка — с основного, его обрыв — перезапуск.
- **Малые кадры**: зрители MJPEG / недавний снимок — `lores.fps`; fnav-watch — его частота; иначе 1 к/с. С основного
  потока при 1 к/с — только ключевые кадры (декодер пропускает остальные): свежий снимок к тревоге почти даром. Второй
  поток декодируется весь (640×360 — ~6 мс процессора на кадр, ~9 % ядра при 15 к/с): задний вид на экране получает
  полную частоту сразу, без ожидания ключевого кадра (у камеры GOP до 2 с). Прореживание — по меткам времени камеры, не
  по приходу: по Wi-Fi кадры приходят пачками, и по приходу из 15 к/с на экран доходило 8,7 (замер 2026-11-01). Спрос
  опрашивается раз в 0,1 с. Ширина `lores.w`, высота — по пропорциям потока (кратно 2). Полный декод основного потока
  дорог (замер на CM4: 2560×1440 — ~46 мс на кадр вместе с уменьшением, 77 % ядра при 15 к/с на почти неподвижной
  картинке; аппаратный h264_v4l2m2m через PyAV — вдвое дороже из-за копий): для экрана и распознавания — второй поток
  камеры (`lores_url`, обычно 640×360). Сети распознавания берут меньше: NanoDet — 416×416, YuNet — вырезку 192 px.
- **Задержка** (замер 2026-11-01 по секундам в подписи камеры, Kruger&Matz Connect C150): fnav-camera-rear + fnav-core
  добавляют к приходу кадра со второго потока ~20–60 мс (декодирование, JPEG, HTTP). Остальное — камера (кодер, Wi-Fi)
  и разбор H.264 в FFmpeg: кадр отдаётся, когда пришло начало следующего (+1 кадр). Обойти разбор нельзя: без него
  кадр приходит кусками без признака конца (RTP marker FFmpeg не отдаёт), а склейка по паузе по Wi-Fi давала бы битые
  кадры.
- **Время**: метки камеры привязываются к монотонным часам при подключении, уход > 2 с — заново, только растут.
  Дату/время на картинку не впечатываем (это перекодирование) — пусть рисует камера (её часы — по NTP с Pi).
- **Сбои**: обрыв/конец потока или нет видео 15 с — перезапуск конвейера (сегмент закрывается); неудачи подряд —
  пауза 5 → 10 → 20 → 30 с. `enabled = false` — ничего не держит (`state = "disabled"`). `record = false` — без записи
  (`state = "live"`). Изменение `rear_camera` (кроме `mirror`) или пароля — `/reload` перезапускает конвейер.
- **Хранилище**: общий лимит и резерв. Передняя чистит все записи (самые старые обеих камер), кроме чужого файла,
  изменённого < 120 с назад (текущий сегмент задней); задняя — только свои. Минимум петли у передней — час записи
  обеих камер (по их битрейтам), у задней — час своей; `protected_gb` / `over_limit` — по тем же записям.
  Восстановление после обрыва питания — каждая свои (передняя не трогает `rear/`). `CameraStatus.current_segment` и `/protect-current` задней — `rear/…`.
- **Экран в машине**: клавиша 4 / кнопка GPS-модуля (`camera_switch`) — задний вид поверх авто-логики карта/камера
  (`display.camera = "rear"`, `reason = "rear"`), повторное нажатие — обратно; зеркально — `rear_camera.mirror`.
- **Звук** (`rear_camera.audio`, микрофон камеры; Connect C150 — G.711 µ-law 8 кГц в обоих потоках): забирает помощник
  второго потока (`rtsp_pull --audio`; нет второго — основного), запись видео он не трогает. PCM s16 моно 8 кГц —
  в `fnav/camera/sound.py` (громкие звуки на охране, [vision.md](vision.md) «Громкие звуки»). Помощник кодирует ещё
  AAC-LC 16 кГц 32 кбит/с (`aac 1` в stdin), пока он нужен: **записи** (`rear_camera.record_audio`, по умолчанию да —
  ~14 МБ в час) и `/live.ts`, пока его смотрят. Дорожка AAC — PID 0x101 в PMT, PCR — на видео; метки звука — на тех же
  монотонных часах, что видео (AAC — на часах PCM, без задержки кодера). Регистратор: первый кадр звука закрывает
  сегмент без звука на ближайшем ключевом кадре, дальше сегменты со звуком; восстановление после обрыва — как было
  (хвост режется по началу последнего PES видео). В `/live.ts` звук пропал дольше 0,5 с — мультиплексор дописывает
  тишину (кадр тишины помощник шлёт первым), иначе браузер (MSE, звук с видео вместе) встаёт; в записях пропуски
  закрывает плеер (hls.js). `CameraStatus`: `audio` ("pcm_mulaw 8000 Hz" или null), `sound_armed`, `sound_level_db`
  (1 с), `sound_seq`. WebRTC (MediaMTX) звука не несёт: админка со звуком смотрит `/live.ts`.
- **Динамик камеры** (сирена) недоступен: у Connect C150 нет обратного аудиоканала ONVIF (в SDP с `Require:
  www.onvif.org/ver20/backchannel` его нет, выход звука в профиль не подключается: `AddConfiguration` отвечает 200,
  но `UseCount` остаётся 0, а прошивка после этого перестаёт пускать новых клиентов к `profile0` до перезагрузки —
  не повторять). Говорить через неё можно только из приложения Tuya.

## Режим разработки (на ПК, без камеры)

- `python -m fnav.camera --fake [--camera rear]` — вместо Picamera2 / RTSP источник тестового H.264 (например, ffmpeg `testsrc` → H.264 Annex-B, если ffmpeg есть) или синтетические кадры; MJPEG — тестовая картинка.
- Тест «обрыв питания»: писать сегмент, в случайный момент убить процесс (`SIGKILL`) / обрезать файл на случайном байте → после «перезагрузки» файл обрезается до целых пакетов и полностью декодируется (ffprobe/PyAV), потеря ≤ `fsync_interval_s` + 1 с.
